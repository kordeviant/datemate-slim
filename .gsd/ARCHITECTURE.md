# DateMate Architecture

> Generated by codebase mapper on 2026-11-19

## Overview
DateMate is a production-grade dating, social discovery, and real-time messaging backend built as a **Modular Monolith** using **Domain-Driven Design (DDD)** and **Clean Architecture** patterns in **Go 1.25** (`go.mod:1-3`, `cmd/server/main.go:42`).

The system cleanly separates business domains (`auth`, `users`, `matching`, `recommended`, `friends`, `chat`, `media`, `notifications`, `questions`, `interests`, `admin`, `system`) from platform infrastructure (`internal/platform/database`, `internal/platform/redis`, `internal/platform/storage`, `internal/platform/fcm`, `internal/platform/geo`, `internal/platform/mail`).

### Key Invariants & Architectural Rules
1. **Single Canonical Contracts**: No duplicate payload fields, no route aliases, and strictly no DTO fallback aliases (`City`, `cityName`, `fcmToken`, etc.) (`ARCHITECTURE.md:13-20`, `GEMINI.md:32-48`).
2. **Deterministic Direct Messaging**: 1-on-1 conversations compute an RFC 4122 v5 UUID derived from a canonical pair `min(userA, userB):max(userA, userB)` to eliminate race conditions (`internal/common/canonical_pair.go:12-26`).
3. **Partitioned Real-Time Timeline**: Message persistence in PostgreSQL is partitioned by daily bucket (`bucket = YYYYMMDD`) with idempotency deduping (`internal/modules/chat/service.go:150-200`, `internal/common/time_bucket.go:1-20`).
4. **Decoupled Asset System**: Media uploads are validated via binary magic bytes and stored under relative paths, with public URLs dynamically resolved using environment configuration (`internal/common/asset_url.go:16-50`, `internal/platform/storage/validator.go:37-60`).
5. **Feed & Recommendation Invariant**: Eligible discovery candidates strictly enforce `User.profileValidated == true` without mandating an existing selfie (`internal/modules/matching/service.go:77-84`, `internal/modules/recommended/service.go:190-210`, `GEMINI.md:105-108`).

## Data Flow

### 1. User Authentication & Session Establishment
1. Client issues `POST /v1/auth/signin` with email/username and password (`internal/modules/auth/handler.go:36`).
2. `auth.Service` queries `users` by lowercased identifier, verifies bcrypt password hash, and creates a record in `user_sessions` (`internal/modules/auth/service.go:110-160`).
3. Service generates signed JWT Access Token (15m expiry) and Refresh Token (30d expiry) embedding `userId` and `sessionId` (`internal/modules/auth/service.go:165-195`).
4. Response envelope wraps tokens and user profile for client persistence (`internal/middleware/envelope.go:41-80`).

### 2. Candidate Discovery & Swipe Flow
1. Client requests `GET /v1/feed` with active JWT (`internal/modules/matching/handler.go:32`).
2. `matching.Service` inspects the user's demographic gender and executes an anti-join query (`FindFeedCandidatesWithNotExists`) in PostgreSQL to fetch candidate users who have `profileValidated = true` and have not yet been swiped (`internal/modules/matching/service.go:76-84`).
3. Client submits swipe `POST /v1/swipes` (`targetUserId`, `direction: "RIGHT"` | `"LEFT"`).
4. `matching.Service` executes Redis Lua script (`swipeLuaScript`) to atomically register the swipe and check if a mutual right swipe exists (`internal/platform/redis/client.go:25-48`).
5. Asynchronously inserts swipe record into PostgreSQL `swipes` table. If mutual, writes to `matches` table and triggers a non-blocking push notification via `fcm.Dispatcher` (`internal/modules/matching/service.go:150-180`).

### 3. Recommendation Scoring Flow
1. Client requests `GET /v1/recommended` (`internal/modules/recommended/handler.go:31`).
2. `recommended.Service` checks Redis cache (`GetRecommendedCache`). If missed, queries eligible validated candidate profiles from PostgreSQL (`internal/modules/recommended/service.go:138-160`).
3. For each candidate, computes 5 component scores: Questions (35%), Interests (25%), City (20%), Relation (10%), Age (10%) (`internal/modules/recommended/service.go:253-260`).
4. Results are sorted descending by compatibility score, cached in Redis for 24 hours (`RECOMMENDED_CACHE_TTL`), and returned to the client (`internal/modules/recommended/service.go:261-285`).

### 4. Real-Time Messaging & Direct Chat Flow
1. Client establishes WebSocket connection to `/socket.io` or `/chat` with JWT authentication in handshake auth/query (`internal/modules/chat/gateway.go:197-235`).
2. Direct 1-on-1 conversation lookup or creation derives deterministic conversation UUID via `GenerateDeterministicConversationID` (`internal/common/canonical_pair.go:24-26`).
3. Client emits `message.send` event with `{ conversationId, content, clientMessageId, replyToMessageId, attachments }` (`internal/modules/chat/gateway.go:475-520`).
4. `chat.Service` checks `message_idempotency` table. If unique, saves message into `messages_by_conversation` under the day bucket partition `YYYYMMDD` (`internal/modules/chat/service.go:160-210`).
5. Real-time gateway broadcasts `message.created` to room participants. If recipient is offline, enqueues high-priority `CHAT_MESSAGE` push notification to `fcm.Dispatcher` (`internal/modules/chat/gateway.go:530-560`, `internal/platform/fcm/dispatcher.go:23-33`).

## Conventions

- **Naming:**
  - Go packages: Lowercase single-word bounded context names (`auth`, `users`, `chat`, `matching`, `geo`, `storage`) (`cmd/server/main.go:16-34`).
  - DTOs and Structs: UpperCamelCase with descriptive suffixes (`FeedCandidateDto`, `RecommendedCandidateDto`, `PushNotificationPayload`) (`internal/modules/matching/dto.go`, `internal/modules/recommended/dto.go`).
  - Database schema: Snake_case table and column names (`user_sessions`, `messages_by_conversation`, `profile_validated`) (`internal/platform/database/schema.sql:50-299`).
- **Structure:**
  - `cmd/`: Application binaries and CLI entry points (`cmd/server/main.go`, `cmd/seed/main.go`).
  - `internal/modules/<domain>/`: Modular monolith domain contexts containing `handler.go`, `service.go`, `dto.go`, and domain test files.
  - `internal/platform/<infra>/`: Shared infrastructure drivers (database, redis, storage, geo, mail, fcm).
  - `internal/middleware/`: Global and route-level HTTP middlewares (envelope, auth, throttler, docs).
  - `internal/common/`: Domain-agnostic utilities (canonical UUID pairs, opaque cursors, asset URLs, time bucketing).
  - `migrations/`: Sequential `.up.sql` and `.down.sql` database schema migrations.
  - `test/`: End-to-end integration test suites (`test/trello_*_test.go`, `test/route_parity_test.go`).
- **Testing:**
  - Unit & Integration testing: Go native `testing` package with table-driven test cases and pgxpool/redis integration tests across all modules.
  - Concurrency discipline: Parallel test execution throttled via `-p 4` or `--maxWorkers=4` to protect host memory.
  - Automated verification: Comprehensive Node.js E2E scenario suite (`datemate-e2e/runner.mjs`, `scenarios/01-08`).

## Explicit Unknowns
1. **Production FCM Credentials & Project ID**: The specific production Google Firebase service account JSON is not checked into source control; development defaults to mock mode (`FCM_MOCK_MODE=true` in `internal/config/config.go:99,223`).
2. **Third-Party CDN Domain**: The production CDN hostname is injected via `ASSET_BASE_URL` or `APP_BASE_URL` at runtime (`internal/config/config.go:120-126`).
3. **External SMS Gateway**: Authentication currently relies on email OTP and test verification tokens; an external telecom SMS provider (e.g. Kavenegar, Twilio) is not yet wired into `internal/modules/auth/service.go`.
